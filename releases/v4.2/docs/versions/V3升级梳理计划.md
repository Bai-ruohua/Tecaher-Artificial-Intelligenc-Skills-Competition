## 一、需求逻辑梳理

用户提出 3 个核心诉求 + 1 个流程诉求：

| # | 用户诉求 | 当前痛点 | 目标 |
|---|---------|---------|------|
| 1 | **不只是 Python，任意课程都能用** | 章节(12章)、雷达维度(5维)、知识库全部硬编码在 `knowledge_base.py` / `data_sync.py` / `rag_engine.py`，换课程必须改代码 | 课程成为"顶层租户"，章节/模块/知识库全部数据化，上传资料即生效 |
| 2 | **学生端功能应在教师端体现** | 4 大 AI Agent（RAG问答/出题判分/数字人讲解/知识图谱）只在学生端页面，教师只能用备课/命题/批改/学情 | 教师端同样开放 4 大智能体，师生"共用一套能力、不同角色 UI" |

## 二、总体设计理念：Course as Tenant（课程即租户）

把"课程"提升为平台的一等公民。平台本身是一个**通用的 AI 教学引擎**，一门课程通过"喂入三件套"即被实例化：

```
一门课程 = 课程体系(章节/模块) + 知识库(上传文档) + [题库(可选)]
                │                    │
                ▼                    ▼
        course_chapters      course_documents (RAG 切片)
                │
                ▼
        questions / student_attempts 均带 course_id
```

所有能力（RAG / 出题 / 数字人 / 图谱 / 雷达 / 排名 / 甘特）都**以 `course_id` 为作用域**，互不串门。
新增一门《高等数学》或《计算机网络》，只要上传大纲 + 课件，平台原样支持，无需改一行业务代码。

## 四、数据库变更

### 4.1 新增表 `course_chapters`（课程体系数据化，取代 knowledge_base.py 硬编码）
```sql
CREATE TABLE course_chapters (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    course_id INTEGER NOT NULL REFERENCES courses(id),
    chapter_id TEXT NOT NULL,         -- 如 ch01（课程内唯一）
    seq INTEGER DEFAULT 0,            -- 章节顺序
    title TEXT NOT NULL,
    level TEXT DEFAULT '',            -- 入门/基础/进阶/综合
    module TEXT DEFAULT '',           -- 【关键】模块/维度名，用于雷达聚合（如"基础语法"）
    keywords TEXT DEFAULT '[]',       -- JSON
    objectives TEXT DEFAULT '[]',     -- JSON
    key_points TEXT DEFAULT '[]',     -- JSON
    difficulties TEXT DEFAULT '[]',   -- JSON
    meta_json TEXT DEFAULT '{}',      -- 富文本（练习问答/代码示例等）
    UNIQUE(course_id, chapter_id)
);
```

### 4.2 新增表 `course_documents`（按课程的知识库切片）
```sql
CREATE TABLE course_documents (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    course_id INTEGER NOT NULL REFERENCES courses(id),
    chunk_text TEXT NOT NULL,         -- 切片文本
    source_file TEXT DEFAULT '',
    chapter_id TEXT DEFAULT '',       -- 可选：归属章节
    embedding TEXT DEFAULT '',        -- 向量(JSON)；无向量库时用关键词/TF-IDF
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 4.3 改造现有表：补 `course_id`（实现按课程隔离）
| 表 | 变更 |
|----|------|
| `questions` | 加 `course_id`（已有 `chapter_id`） |
| `student_attempts` | 加 `course_id`（排名/雷达按课程聚合，避免数学题污染 Python 雷达） |
| `wrong_books` | 加 `course_id` |
| `mastery_timeline` | 加 `course_id` |
| `ability_scores` | 已有 `course_id`，继续使用 |

### 4.4 种子数据
- 原 `knowledge_base.py` 的 12 章 Python 内容 → 作为"示例课程"种子，写入 `course_chapters`（course_id 指向已存在的 Python 课程），`module` 按现有 5 维映射填入。
- `knowledge_base.py` 保留为"种子常量源"，不再被运行时直接引用，改由 DB 提供 `get_course_chapters(course_id)`。

## 五、课程体系数据化方案

- `knowledge_base.py` 重构：`get_course_chapters(course_id)` / `get_chapter(course_id, chapter_id)` 改读 DB。
- 教师"课程管理"页支持：
  - **手动建章节**：填标题、选/建模块（维度）、贴关键词与目标；
  - **大纲智能解析**（进阶）：上传 syllabus，调用 DeepSeek 抽取章节结构并自动写入 `course_chapters`；
  - **Python 示例课程**：一键载入种子 12 章。
- 雷达维度 = 该课程 `course_chapters` 中去重后的 `module` 集合，由数据驱动，**删除 `data_sync.py` 中的 `ABILITY_DIMENSIONS` 硬编码**。

## 六、知识库按课程隔离（上传即建库）

新增 `modules/knowledge_store.py`：
- `ingest(course_id, file_path)`：解析 PDF/DOCX/TXT → 切片 → 存入 `course_documents`（带 course_id）。
- `retrieve(course_id, query, top_k)`：仅检索该课程切片（关键词 + TF-IDF / 可选向量）。
- `rag_engine.py` 改造：`RAGEngine(course_id)` 或 `retrieve(course_id=...)`，不再引用全局 `CHAPTERS`。
- 教师"知识库管理"页：上传文档、查看切片数、重建索引、删除。

## 七、教师端开放 4 大 AI 智能体（师生共用一套能力）

将学生端 4 个 Agent 的能力层（`modules/student_agents.py`、`exam_generator`、`digital_human`、`knowledge_graph`）解耦为**角色无关**，师生共用同一套 API；路由层对两种角色都开放（`@login_required` 即可，按角色渲染不同 UI）。

| 智能体 | 学生端用途 | 教师端用途 |
|--------|-----------|-----------|
| RAG 智能答疑 | 学生提问、溯源 | 教师备课查资料、课堂演示问答 |
| 智能出题与判分 | 学生刷题自测 | 教师预览/生成题目、布置练习 |
| 数字人讲解 | 学生看讲解视频 | 教师生成讲解视频用于授课 |
| 知识图谱 | 学生查看知识网络 | 教师查看/编辑课程知识图谱 |

新增教师端页面：`/teacher/qa`、`/teacher/exam-preview`、`/teacher/digital`、`/teacher/graph`，复用既有 API。

## 九、雷达 / 甘特 / 排名 动态化（去除硬编码）

- **雷达**：`compute_radar_data(student_id, course_id)` 读取该课程 `module` 集合，按 `module` 聚合章节答题，维度数由数据决定。
- **甘特**：`compute_gantt_data(student_id, course_id)` 遍历该课程 `course_chapters`，不再遍历全局 `CHAPTERS`。
- **排名**：`compute_ranking(course_id=...)` 在 `student_attempts` 中按 `course_id` 过滤（已有参数，补过滤逻辑）。

## 十一、版本管理方案（"版本闸门"流程）

每次更新（含本次 V3）必须执行：
1. **更新 `CHANGELOG.md`**：记录版本号、日期、范围、破坏性变更。
2. **留存方案快照**：本计划存入 `docs/versions/V3升级梳理计划.md`。
3. **留存代码快照**：`releases/v3.0/`（Python 脚本复制源码，环境无关，可回滚）。
4. **版本号常量**：`config.PLATFORM_VERSION = "3.0"`，页脚与 `/api/version` 展示。
5. （可选）若环境支持 git：`git tag v3.0`（本沙箱 git 不可用，改用 releases/ 快照）。

回滚方式：用 `releases/vX.Y/` 覆盖当前 `app.py`/`modules/`/`templates/` 等源码即可。
